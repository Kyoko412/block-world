## 二、会空转/自相矛盾的地方

### P7 Skills 不存在时怎么办（§5 开头补一段）

**新增**：

```
如果当前环境没有安装上述 Skills：不要停下来找安装包，用等价流程继续：
  grilling        → 直接向用户提问，把边界问清楚
  to-spec         → 在 docs/current/ 写一份简短规格
  to-tickets      → 把工作拆成可独立验证的条目
  implement       → 实现 + 自测 + 自审
并在报告里注明"以流程替代 Skill：<原名>"。
**首次接管会话不调用任何 Skill。**
```

### P8 首次接管与"停止条件"重复（§2 与 §14）

两节讲的是同一件事，建议把 §14 精简成：

```
### 14. 首次会话的停止条件

完成 §2—§4 与 §8 的核验后，输出 §14 要求的七项内容，然后**停止**：
不写代码、不提交、不调用 Skill、不开始待办。
等用户用一句话指定第一批任务（例如"做 H"）后再继续。

之后每轮以本协议 + 仓库当前事实为基线，不重新设计整个项目。
```

### P9 术语不统一

`证据包` / `工作单元` / `任务` 三种说法混用。建议统一成 **证据包**（因为它绑定"命令+证据+限制"），
并在 §8 定义一次："一个证据包 = 一项可验证的改动 + 复现命令 + 输出证据 + 已知限制"。

### P10 §12 与 §0 重复

两节都在讲"最小复杂度、局部变更"。保留 §0 的原则，§12 缩成一句：

```
### 12. 长期维护

每次开发只做三件事：明确问题与成功标准 → 最小改动 → 真实验证。
其它（重构、抽象、性能优化）只在新需求明确要求时做。
```

## 三、建议补上的两条工程约定

### P11 提交格式（§9 补）

```
提交信息：`<type>(<scope>): <一句话>`，type ∈ feat/fix/docs/chore/build/test。
正文写"怎么验的"（命令 + 关键输出）。
提交前自查：`git status` 只含本轮文件；本轮验证命令已通过；没有把失败项写成完成。
```

### P12 接管报告别写"未执行的命令"（§14 补）

```
报告里列出的每条命令，必须标注"已执行 / 未执行"。
未执行的写明原因（缺 bash、缺依赖、需人工操作），不得留空让人误以为跑过。
```
