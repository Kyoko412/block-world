## 1. 底线（违反=这一段白干）

- 单测与 e2e 基线始终全绿；只许**新增**断言，不许删改、不许放宽既有断言
- 禁止改 `app\renderer\vendor\three.module.js`、禁止改 `app\package.json` 依赖
- **禁止任何联网下载**：不许 `npm install` / `pnpm add` / `npm ci` / `npx <未装包>` / `git clone` /
  `curl` / `Invoke-WebRequest`。唯一允许的联网是 `web_search`/`web_fetch` **只读查询**
- 不许大规模重构、不许改目录结构
- 存档格式如变更必须兼容旧档（旧档读不出=失败）
- 禁止不加 `--selftest` 直接运行 `方块世界.exe`
- **禁止与 `pack.js` 并行跑自检**（磁盘争抢会让自检超时返回 2）
- e2e 很长：**别用会把进程组一起杀掉的短超时**（120 秒超时曾把 game 进程带走）；
  日志停在「注入验收剧本…」超过 2 分钟不动 → `Stop-Process -Name electron -Force` 后重跑一次

## 2. 检查点纪律（沿用 v2，继续有效）

- 假设你随时会断电——事实上你确实会

## 3. 断言对账（v3 的核心，专治"假绿"）

上一轮的教训：`T3` 第 33 节因为改名漏了声明行，剧本的 `try/catch` 把后面**整节 11 条**吞掉，
日志却写着 `通过 281/281，失败 0`，看起来全绿。退出码 0 完全不可信。

从本轮起，每次改测试都必须做**三件对账**，缺一不算完成：

1. **总数对账**：日志里的 `通过 N/N` 必须等于「上一轮基线 + 本轮新增条数」。
   差一条就要查是不是整节被吞、条件断言没执行、或者重复执行。
2. **名字对账**：新增断言的名字必须能在日志里 `grep` 到（比如 `Q.1`~`Q.8`、`Z.1`~`Z.9`）。
   只看到总数涨了、名字搜不到，等于没跑。
3. **样本量对账**：凡是「某窗口内最大值 < 阈值」的断言，必须配一条「这个窗口里确实有 N 个样本」，
   否则 `maxFrameMs=0` 会让它假绿（上一轮 `T2.5` 就是这么被抓住的）。

另外三条硬规矩：
- **比例型阈值先把来源算一遍再写数字**：上一轮 `E1` 写「80% 的格子应在 power 内」，
  实测外圈抖动带占 31%，这条从写下来就不可能成立（红的是测试不是产品）。
  三维格点、概率带、帧数窗口这类"直觉最不靠谱"的地方，先算/先量，或者改成能表达意图的性质
  （无超出上限 + 多数在内 + 外圈必须存在）。
- **新断言必须先在当前代码上变红**（先红后绿），红色原文贴进进度文件
- **关键断言做一次变异**：把实现改坏，确认断言真的会红；改回。没做过变异的断言不算有牙

### T1 要落地的机制：`EXPECTED_TOTAL`
在 `app\tests\e2e-scenario.js` 顶部加常量，并在剧本末尾加一条自检：
```js
const EXPECTED_TOTAL = 310;   // 每次新增断言后同步 +N
...
ok('总数对账：实得条数 = 基线 + 本轮新增', R.total === EXPECTED_TOTAL,
   '实得 ' + R.total + ' 期望 ' + EXPECTED_TOTAL);
```
这样任何一节被吞掉，这条都会红。**更新 `EXPECTED_TOTAL` 成为每个任务 DoD 的一部分**，
并在进度文件里记「本轮 310 → 312」这种增量。

## 5. 每个任务的完成定义（DoD，六件缺一不可）
1. 代码 + 新增断言（**先红后绿**，红色原文贴进进度文件；关键断言做过一次变异）

- 上下文要省：长日志写进进度文件，对话里只写结论与数字

- 额度/上下文即将耗尽
