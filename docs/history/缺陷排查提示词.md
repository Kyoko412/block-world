# 缺陷排查提示词 · 方块世界

用途：把「主提示词」整段粘给 AI，让它按"先复现、再假设、后修"的顺序排掉玩出来的四个毛病。
前置：项目里已有 `通宵任务提示词.md`（功能开发用），本文件专管**缺陷排查**，两者可同时生效。

## 1. 全程不许破坏（违反=这次排查白做）

- 禁止改 renderer\vendor\three.module.js、禁止改 package.json 依赖

## 2. 每个缺陷的固定流程（照抄，不许跳步）
1. **复现**：优先写成无头断言（world.test.js 里能 assert 的那种）。做不到无头就用 e2e 剧本。
   复现脚本要能稳定重现，并且**先在当前代码上看到它红**，把红色原文贴进 debug\排查日志.md。
2. **二分定位**：从输入 → 状态 → 渲染 三段里，用打印/断言把出错的那一段缩到单个函数。
   写下你的假设和被证伪的假设（这一步必须留痕，不要只写结论）。
3. **最小修复**：只改必要的几行。修完先跑单测，再跑 e2e。
4. **回归守卫**：把第 1 步的复现固化成一条长期保留的断言，命名带 `回归：` 前缀。
5. **验证**：`cd app && node --test tests\world.test.js` → `npx electron tests\e2e-electron.mjs` →
   `node tools\pack.js` → `powershell -NoProfile -ExecutionPolicy Bypass -File app\tools\selftest-package.ps1`
   四条都要贴原始输出（数字/退出码），最后一条必须 EXITCODE=0。
   注意：**自检不要和 pack.js 同时跑**，磁盘争抢会让它超时返回 2。
6. **提交**：`git commit -m "fix(<模块>): <现象> | 单测 x/y | e2e a/b"`，一个缺陷一个提交。

## 3. 六个缺陷（按此顺序，严重度递减）

### D1【最高】启动出错框：`Cannot read properties of undefined (reading 'pickaxe_wood')`
- 现象：游戏里突然弹出红框「启动出错：Cannot read properties of undefined (reading 'pickaxe_wood')」，
  画面仍在渲染（截图里能看到保存提示、快捷栏、生命值都正常），所以**不是启动阶段崩的**，
  是运行中某次操作触发的未捕获异常，被 `renderer\js\main.js` 的 `window.addEventListener('error')` 兜住显示。
- 已知线索（我已核过，可以直接用，别重走）：
  - `pickaxe_wood` 在代码里只出现在两处：`core\items.js:186`（创造物品栏工具页列表）与
    `gfx\painters.js:1484`（itemPainters 里的图标画笔）。**它不是方块 id**。
  - 报错形状是 `undefined['pickaxe_wood']`（对象取键），**不是** `undefined.tiles`。
    所以基本可以排除 `core\blocks.js:240 tileForFace`（那里有 `if (!b) return 'missing'` 保护）
    和 `gfx\painters.js:1641 dispatch`（那里有 `table ? table[name] : null` 保护）。
  - 因此重点排查：**某个"按名字取表"的对象在使用时还没有被初始化**（模块加载顺序/循环引用），
    或**某个表被局部变量遮蔽成了 undefined**。
- 具体要做：
  1. 先找到真实堆栈：在 `main.js` 的 `fatal()` 里把 `err.stack` 也写进红框（或 `console.error` 全栈），
     然后重现一次拿到准确文件与行号。**不要靠猜。**
  2. 复现线索：截图里快捷栏选中的是**木镐**，且游戏已经玩了一会（有存档提示）。
     优先怀疑路径：手持工具时打开背包/创造物品栏并渲染工具图标、丢弃工具（Q）生成掉落物实体、
     工具耐久耗尽消失、创造物品栏工具分页渲染。逐个试，把命中的那条写成断言。
  3. 修复方向：给该查表处补上"表未就绪/键不存在"的兜底（返回 missing 图标或跳过），
     并让红框只在真正的致命错误时出现——**运行中的单次渲染异常不应该弹「启动出错」**。
     具体做法：`main.js` 的 `fatal()` 区分启动期与运行期（启动期才显示红框，运行期 console.error + 计数）。
- 验收：`回归：` 断言在旧代码上红、新代码上绿；红框在正常游玩中不再出现（e2e 加一条断言：
  剧本跑完后 `window.__bootErrorShown === false`，需要在 main.js 暴露这个标记）。

### D2 人物偶尔瞬移
- 现象：玩家位置会突然跳一下（瞬移），偶发、无固定时间点。
- 这是最需要"先复现"的一条，**不许凭感觉改碰撞代码**。
- 首先做一件事：**证明它是否真的发生过**。加一个位置监视器（可用 game.testApi 暴露或临时脚本）：
  每帧记录 `pos`，若单帧位移 > 该帧最大可能速度 × 1.5 就记一条日志（帧号、前后坐标、vel、onGround、
  flying、inWater、当前 UI 状态）。跑 e2e 全剧本 + 手动玩几分钟，看能否抓到。
- 已知可疑点（按怀疑度排序，逐个用上面的监视器验证或排除）：
  1. **每秒自动存档的卡顿**：截图右上角有「上次保存 N 秒前」，若存档是同步写大 JSON，
     会把主循环阻塞一段时间，恢复后 `dt` 变大（`game.js` 有 `dt = Math.min(dt, 0.1)` 钳制），
     单帧位移一次性变大 → 看起来就是瞬移。**这条最可疑，先查它。**
  2. `spawnAt()`（`controller.js:83`）里的「卡进方块就 `pos.y += 1` 顶出」循环：
     若玩家被判定卡进方块，会被连续上顶，表现为垂直瞬移。
  3. 区块加载/卸载时的"传送到 200 格外"类逻辑、`ensureChunk` 后的位置修正。
  4. 界面打开/关闭时是否把玩家位置重置（`respawn` / 读档路径）。
  5. 碰撞逐轴推进在极端 dt 下的穿透与回弹。
- 验收：抓到复现后写成断言（例如：把存档改成异步/分帧后，单帧位移不再超阈值）；
  若最终证明是"卡顿导致的观感"而非逻辑瞬移，**如实写进报告并给出证据**，不要假装修好。

### D3 生物移动朝向不对：往后走、头还朝前
- 现象：动物移动时身体朝向与位移方向不一致（后退着走）。
- 定位方法（很快）：在 `world\mobs.js` 里找到把速度方向转成 `rotation.y` 的那处，
  用一条**纯逻辑断言**验证：给定速度向量 (vx, vz)，期望的 `rotation.y` 与模型正面朝向是否匹配。
  注意 three.js 里 `rotation.y = atan2(dx, dz)` 与 `atan2(-dx, -dz)` 差 180°，
  而"模型正面"到底朝 +Z 还是 -Z 取决于建模时 `lookAt`/几何朝向——**去读 mobs.js 里模型是怎么建的**，
  不要套公式。玩家视角的 `yaw = Math.atan2(-dx/L, -dz/L)`（见 e2e-scenario.js 的 aimAt）是另一套约定，
  别把两者混用。
- 要做：修正朝向计算，并给每种会移动的生物（猪/羊/牛/鸡 + 僵尸/骷髅等敌怪）都补一条朝向断言，
  断言里同时覆盖 8 个方向（+x/-x/+z/-z 与四个斜向），避免只测一个方向碰巧通过。
- 验收：`回归：` 断言覆盖 8 方向；e2e 里"生物朝玩家移动"那条（17.5a）仍通过。

### D4 水下气泡不显示减少、但掉气效果生效
- 现象：潜水时气泡 UI 不随剩余空气变化（不减少），但溺水扣血/呼吸逻辑是生效的。
- **根因已定位（我核过，直接改，不用再查）**：`ui\ui.js:508-514`：
  ```js
  const bubbles = 10 - Math.floor((c.air || 10) / 10 * 10);   // 化简后 = 10 - Math.floor(c.air)
  breath.style.opacity = bubbles > 0 ? '1' : '0.35';
  ```
  `bubbles` 只被拿去算**整个元素的透明度**，**从来没有删掉/隐藏单个气泡**。
  气泡只在 `eyeInWater` 首次为真时建满 10 个，之后不再变化；出水时 `breath.innerHTML = ''` 直接清空，
  所以恢复过程也看不到。空气逻辑本身是对的（`controller.js:218-222` 维护 `air`，水下 `air -= dt`、出水 `air += dt*4`）。
- 要做：
  1. 改成按 `air` 逐个控制气泡：剩余空气数 = `Math.ceil(c.air / 10 * 10)`（即 `ceil(air)`），
     逐个设置 `display`/`opacity`/`visibility`，让它们真的一个个消失；满气时整条不显示（opacity 0）。
  2. 出水时保留元素、让气泡逐个恢复，恢复到满再把整条淡出；不要再用 `innerHTML = ''` 直接清空。
  3. 加 e2e 断言，像 `T1.11`/`T3.8` 那样断言**具体 DOM 值**而不是只看元素存在：
     空气 10 → 可见气泡 10；把 `air` 设到 5 → 可见气泡 5；设到 0 → 0；
     再把 `air` 调回 10 → 恢复 10。两个方向都要覆盖。
- 验收：`回归：` 断言覆盖"减少"与"恢复"；`UI 更新必须每帧生效`（现在这个 bug 正是只在条件分支里更新）。

### D5 创造模式下按 F / 双击空格不能飞行
- 现象：切到创造模式后按 F 或双击空格，人不会飞。
- **测试缺口（这是关键）**：现有 e2e `9.2 创造模式可飞行` 是**直接调用 `controller.toggleFly()`** 验证的，
  **完全绕过了 F 键与双击空格两条真实输入路径**，所以断言全绿也挡不住这个 bug。
- 已知代码路径（都读过了）：
  - `game.js:277-281` F 键 → 若 `controller.creative` 才 `toggleFly()`，否则 toast「只有创造模式可以飞行」
  - `game.js:250` 双击空格 → 同样要求 `controller.creative`
  - `controller.js:434-439` `toggleFly()`：`if (!this.creative) return false`
  - `controller.js:163` 飞行时改用 flySpeed；`game.js:115` 建世界时 `controller.creative = meta.mode === 'creative'`
  - `game.js:169` 读档时 `flying = !!data.player.flying && controller.creative`
- 要做的第一步是**判定到底是哪一环**，不要直接改代码：
  1. **先确认模式状态**：按 F 时有没有弹出「只有创造模式可以飞行」？
     - 弹了 → `controller.creative` 是 false，问题在"模式没真正切过去"（重点查 `setMode`／读档路径／
       `meta.mode` 与 `controller.creative` 不一致）。
     - 没弹 → 说明 `creative` 是 true，问题在 F 键没送达或被别的处理抢先（重点查 `input.js` 的 keydown →
       `onKey` → `onKeyCode` 链路，以及 `openUI`/指针锁定时是否吞键）。
  2. **双击空格**单独验：查 `input.js` 里双击判定窗口（现有 e2e 拿它当"双击空格"用，说明有实现），
     确认它是否只在 `onGround` 时才触发、以及在创造模式下是否被跳跃逻辑抢先。
  3. 飞行开着之后按空格/Shift 能否升降（`controller.js:163-190` 那一段的垂直速度处理）。
- 必须补的断言（这是本次最重要的产出）：**e2e 里用真实按键事件走完整链路**——
  `T.key('KeyF', true/false)` 切换后断言 `controller.flying === true`，并断言按空格后 `pos.y` 上升、
  按左Shift 后下降；双击空格路径同样补一条。**不许再用直接调 `toggleFly()` 的方式验收。**
- 验收：新断言覆盖 F 键与双击空格两条路径 + 升降；旧 `9.2` 保留（它验的是 API 层，仍有价值）。

### D6 创造模式下左下角还显示爱心
- 现象：创造模式里左下角血条（爱心）仍然显示。
- **根因已定位（我核过）**：`ui\ui.js:507` 只隐藏了饥饿条——
  ```js
  hunger.style.opacity = c.creative ? '0' : '1';
  ```
  **没有对应的 `hearts` 那一句**。原版创造模式血条与饥饿条都不显示，这里漏了一半。
- 要做：
  1. 补上 `hearts.style.opacity = c.creative ? '0' : '1';`，并检查 `#breath` 在创造模式下的行为是否也需要一致处理。
  2. 顺带确认"隐藏"用 opacity 还是 `display`：既然饥饿条用 opacity，就保持同一套写法，
     不要引入新的隐藏机制（避免布局跳动与既有断言冲突）。
  3. 加 e2e 断言：切到创造 → `#hearts` 的 opacity 为 0（读 `style.opacity` 断言具体值）；
     切回生存 → 恢复为 1。**两个方向都断言**，防止只测一半。
- 验收：断言覆盖切换两方向；确认切回生存后爱心数量与填充状态正确（血量没被改坏）。

## 4. 反假完成硬规则
- 只有四条验证命令都跑过并贴出**真实输出**，才允许写「完成」
- 禁止「应该可以」「理论上修好了」「已修复，未测试」这类措辞；没跑就是没做
- 自己新增的断言必须是**先在当前代码上确认红**的，把红色原文贴进日志（先红后绿）
- 修不动就如实标 `未修复` 并写清卡在哪一步、你排除了哪些假设；**假装修好是最严重的错误**
- 如果某个缺陷最终判定"不是 bug，是设计如此/观感问题"，也要给证据，不要硬改

## 5. 卡住与防挂死
- 同一个缺陷修 3 次仍不通过 → 放弃该缺陷、git 回滚、日志写 `✗ D{n} 放弃：<报错原文前 5 行>`，进入下一个
- e2e 或自检疑似卡住（>15 分钟无输出）→ `Stop-Process -Name electron -Force`，
  改跑单测继续推进，并在日志记 `⚠ 超时`
- 绝对禁止：等待用户输入、问问题、留下 TODO 就停、直接跑 GUI exe 而不带 --selftest
- 上下文要省：不要把长日志整段贴进对话，写进 `debug\排查日志.md`，对话里只写结论和数字

## 为什么这样写（给自己看，不必粘给 AI）

| 提示词里的设计 | 防的是什么 |
