### 缺陷修复 D3：生物倒退着走（头还朝前）

- **根因（读模型建出来的，不是套公式）**：`world/mobs.js` 里猪/牛/羊/鸡的 `head`、`nose` 都摆在模型**+Z** 方向，

  而 `ai()` 的漫游位移写的是 `wantX = -sin(yaw)`、`wantZ = -cos(yaw)`（玩家视角那套约定），
  两者差 180° → 身体朝后走、头朝前。`blockInFront()` 也用同一套反号约定（所以「前方有障碍就跳」实际在探测身后）。
  敌怪追击分支的 `yaw = atan2(-dx,-dz) + PI` 恰好是对的，所以只有动物倒退，僵尸/骷髅正常 —— 与玩家观察一致。
- **复现（先红，原文）**：新增无头断言 `回归：生物移动方向必须与模型正面一致，不能倒退着走（D3，8 个方向）`，

  ```
  ✖ 回归：生物移动方向必须与模型正面一致，不能倒退着走（D3，8 个方向） (28.2768ms)
    AssertionError [ERR_ASSERTION]: 方向 (1,0)：位移必须与模型正面同向，实得点积=-1.000（负值=倒退着走）
  ℹ tests 29 / pass 28 / fail 1
  ```
- **修复**：`ai()` 的漫游位移与 `blockInFront()` 的探测方向统一改为 `(+sin, +cos)`（4 行，含注释）。
- **守卫覆盖**：8 个方向（±X、±Z、四个斜向）× 被动生物，外加 4 个方向的敌怪追击分支

### 缺陷排查 D2：人物偶尔瞬移 —— 未复现「逻辑瞬移」，量化证据在此（没有为此改碰撞代码）

- **做法**：不靠感觉。`player/game.js` 加逐帧位置监视器 `monitorPosition()`，每帧比较
  「实际位移」与「该帧物理时间能解释的最大位移」（`|v|×dt×1.6 + 0.35`，刻意传送后 2 帧不计、
  自动上台阶单独给 1.15 格额度），超出就记录帧号/前后坐标/vel/onGround/flying/inWater/界面状态；
  同时记录帧耗时与自动存档同步段耗时。读数经 `testApi().posMon()` 暴露，写成 7 条断言 `回归.D2a`~`D2g`。
- **实测**（整局剧本累计，覆盖跑动/挖掘/战斗/游泳/读档/死亡重生/连续开关界面）：
  **累计 6648 帧、可疑位移 0 次**；采样窗口内 `saveSyncMs=1`、最大帧 24ms、慢帧 0。
  反空过检查都在：`D2c` 存档确实发生过、`D2f` 自动上台阶确实发生过且**豁免分支真的被用到**、
  `D2g` 绕过 `spawnAt` 人为挪 5 格必须被抓到（抓到 `d=5 limit=0.6`）——证明「0 跳变」不是监视器瞎了。
- **五条嫌疑逐条落地**：① 同步存档阻塞：实测 1ms，且 `dt` 被夹两次（`loop` 0.1s、`update` 0.05s），
  卡 2.5 秒也只推进 0.05 秒物理 → 只会「时间冻结」不会跳位；② `spawnAt` 顶出：新增单测证明**最小且有界**，

  ③ 区块流送：未加载区块的碰撞用 `heightAt()` 纯函数近似（地表及以下算实心），且洞穴限制在 `y < h-1`，脚下不会被挖空；
  ④ 界面开关/读档重置位置：累计 0 跳变；⑤ 极端 dt 穿透：按 0.4 格分步推进且按物理时间判定。
- **顺带修掉的一个真缺陷（在监视器自己身上）**：自动上台阶的豁免额度原靠跨帧旗标，实测
  `tryStepUp 执行=1 事件送达=1 监视器记账=0`——剧本在同一批同步代码里紧跟着调了 `spawnAt`，
  旗标被暂停分支清零，豁免整批丢失（既让计数不可信，也可能把正常抬升误报成瞬移）。
  改为「事件处自增 + 计数增量决定豁免」，并新增 `allowHits` 断言豁免分支真的走到过。
- **判定**：**未复现**逻辑瞬移；玩家能感到的等价现象是**长帧卡顿**（读档/批量改方块时最长 2547ms 一帧，
  累计 16 个慢帧），属于分帧时间预算问题，已单列为待办而不是冒充成「修好了瞬移」。

  目标选择点从「眼睛高度减 1.2」改成身体几何中心 —— 原来的判定对 1.9 格高的村民落在膝盖，
  玩家看着头也点不中（牛/羊/狼同样受益，已有用例全部保持）。
- **三条真实交易**：10 小麦 → 1 绿宝石；1 绿宝石 → 3 面包；3 绿宝石 → 1 铁锭。
  扣料前先检查数量，材料不足时**一颗也不扣**、面板不关；产物放不下时余量掉在脚下，不吞物品。
  面板显示每条交易的材料图标、数量与「背包拥有数」，交易后立即重建。
- **存档与兼容**：村庄方块走现有 chunk diff；站点元数据 `village` 与村民的家坐标 `hx/hy/hz` 入档；
  旧存档没有这些字段时照常读取，不会生成村庄也不会报错。
- **顺手修掉的存档缺陷**：区块远离玩家被卸载时，原先只存在于内存里的方块改动会从下一次存档中消失

  重新加载时照常应用；新增单测 V5 钉住「卸载 → 序列化 → 重新生成 → 改动仍在」。

  穿过多轮存档读档后门/水渠/小麦/工作台/箱子逐格仍在；真实右键村民打开面板（3 条交易、不举盾）；

### 生物互相推开（2026-10-13 长期作业轮新增，5 条单测 + 5 条 e2e 断言，关掉旧「已知问题」#6）

- **闸门为什么不能用 `canStandAt`**：它额外要求「脚下正好压着整数格」，而真实落地 y 常是 `40.9999…`，

- **玩家不受影响**：生物与玩家仍然可以互相穿过（原版如此），e2e `SP.4` 实测玩家位移 `0.00000`。
- **实测**：单测 `M1~M5`（重叠必须被推到互不重叠 / 本来不重叠的不许乱动 / 贴墙不许穿墙 /
  不许动到玩家 / `update()` 里确实调用了）；e2e `SP.1~SP.5` 在真实主循环里把六只羊叠成一坨
  （最小间距 `0.028`）→ 轮询到 `≥0.5` 为止并记录用时，过程中没有一只卡进方块，
  贴墙的四只猪也始终留在墙的一侧。

### 分帧预算：读档与批量改方块不再冻结画面（2026-10-23 长期作业轮新增，5 条单测 + 10 条 e2e 断言，关掉旧「已知问题」#20）

先量化再动手（`cd app && npx electron tests/perf-probe.mjs` 是本轮新增的取证脚本，只测量不断言）：
一个区块的三段成本是 **生成 2.5ms / 补光 1.2ms / 重建网格 10.5ms**（半径 6 = 137 个区块），
所以真正的长帧有两个来源 ——
① **读档前一次性灌完整个世界**（实测同步 1063~1232ms，而且这段时间主循环还没启动，位置监视器整局只看到 1 帧）；
② **批量改方块时逐格 `refreshImmediate`**（实测 250 格 = 1993ms 全在同一个同步段里，帧间隔 1850~2133ms）。

| 口径 | 改前 | 改后（同一台机器实测，连跑三遍） |
| --- | --- | --- |
| 批量 250 格的同步段 | 1980~1993ms | **1ms**（只改数据 + 标脏） |
| 该窗口的最长帧 | 2133ms | **17ms**（排队约 100ms 排空） |
| 读档期间最长帧 | 看不见（只有 1 帧）→ 累计口径 2547ms | **100~133ms**（36~37 帧、单片峰值 ≤60ms） |
| 读档墙钟 | 1716ms | 1785~1816ms（+70~100ms，换来的是不冻结） |
| 整局累计最长帧（D2e 读数） | 2547ms | **200~300ms** |

**做了什么**：
1. `world.js` 导出 `FRAME_BUDGET`（每帧 9ms：gen 3.6 / light 3.0 / mesh 3.4）与 `LOAD_SLICE_BUDGET`（分片 48ms），
   `update()` 改成三段各自 `min(本帧硬上限, 段起点 + 段预算)`，前段没花完的时间可以借给后段；
   光照与网格排队都改成**近处优先**（原来是 Set 的插入顺序，玩家脚下那块可能排在远处后面）。
2. **每段至少推进一个区块**：预算的语义是「尽量不超时」，不是「超时就不干活」——
   否则机器一慢就每帧零进展、读档永远完不成。这条被单测 `分帧 F5` 钉住。
3. 读档分片化：`pumpWorldLoading` 从一次性同步改成「主循环先跑起来（新状态 `loading`，只做环境与渲染、
   不做物理）→ 每片 48ms → 片间让出 RAF（RAF 被节流时用 50ms 定时器兜底）」，
   加载中画面每 3 帧才渲染 1 次（遮罩是半透明模糊的，20fps 足够，省下的 CPU 直接变成更快的加载与更小的帧间隔）。
4. 批量改方块交给排队：`testApi.setBlock`、作物成熟、耕地随机刻都不再逐格同步重建；
   **玩家真实挖掘 / 放置仍然同步刷新那一格**（手感不变）。加载进度条 `ui.setLoadingProgress()` 真的跟着分片走。
5. 新增观测量：`world.perf`（各段耗时、区块数、单区块峰值、本帧顺序）、`world.pending()`、`Game._loadStats`
   （分片数 / 单片峰值 / 同步准备段 / 是否撞 deadline / 是否被取消），testApi 暴露 `worldPerf()` / `worldPending()` / `loadStats()`。

**进度条的口径是自己写错又自己修掉的一处**：第一版用「剩余排队项 ÷ 起始排队项」当进度，
但**生成一个区块会额外产生两项待办**（补光 + 网格），队列中途比起点还大 → 分数被夹在 0 →
进度条会长时间贴在 4% 再突然冲到头。改成「已网格化的区块数 ÷ 本次要网格化的总数」，单调递增、结束时到 1。
顺手还修了「条会往回跳」：点存档时界面先把条写成 20%~25%，而第一片进度是 0%（→4%），于是画面出现倒退；
现在 `setLoadingProgress` 在没到 100% 之前只允许往前走。
闸门也为此改过一次：先写的 `fracAvg > 0.35` **没有牙**（变异回错公式实测 fracAvg 也有 0.32~0.34，只差 0.01），
换成症状本身 —— 有多少片的进度还是 0（`fracStalls`）：正确实现 **0 片 / 平均 0.50**，错公式 **10 片 / 平均 0.32**（同一台机器变异实测）。

**防假实现**（e2e 第 32 节 回归.T2.1~T2.10）：最长帧小可以靠「少灌区块」或「让主循环别跑」刷出来，所以
`T2.4` 要求读档窗口内帧数 ≥10、`T2.7` 要求三段排队清零且 137 个区块一个不少、`T2.3` 要求那 250 格方块数据仍在、
`T2.9` 要求读档后位置与保存一致（Δ=0.0000）、`T2.8` 要求脚下仍是实心方块（分帧不许把人塞进虚空）、
`T2.6` 还要求进度条**从第一片就在动**（`fracStalls ≤2` 且 `fracAvg >0.4`）。

**过程中修掉的一条自己引入的回归**：主循环被提前到「以前根本没有帧」的时间窗里，于是位置监视器第一次看到
读档期间的位移 —— `回归.D2e` 报 `累计跳变=5`，样例 `pos=[0.5,40,0.5] state=loading dx=-180`：那是刚 new 出来
的 controller 默认位置，不是瞬移。改法是 `_loadingWorld` 期间**只记帧耗时、不做位移判定**，出加载态第一帧只重设基线。

**遗留（如实）**：单个区块是不可分割的工作量（常规值 生成 2.5 / 补光 1.2 / 网格 10.5ms，实测峰值 5.8 / 18.7 / 25.3ms），
所以「有待办的帧」最差仍是 预算上限 + 一个区块 ≈ 60~90ms，做不到任意小；要再压就得把网格化本身切片（未做）。
读档墙钟比改前多约 70~100ms，换来的是画面不冻结 + 进度条可读。

### 被方块埋住时的顶出保护（2026-10-23 长期作业轮新增，5 条单测 + 8 条 e2e 断言，关掉旧待办 T3）

**旧行为**：只有 `spawnAt`（读档 / 重生）会把卡进方块的人顶出来。于是两种真实场景会把玩家卡死：
① 走到流式边界、区块在脚下刚好生成完；② 树苗长在玩家站的那一格（树干直接从身体里长出来）。
表现是「人被塞进石头/原木里，按键一步都动不了」——因为 `moveAxis` 的兜底是「对齐后仍相交就整步回退」。

**现在的规则**（`controller.pushOutOfSolid()`，主循环每帧在 `world.update` 之后调用一次）：
1. 只有身体真的与实心方块重叠才动手；
2. **只在 AABB 覆盖到的区块都已真正生成之后**才动手（`chunksAroundReady()`）——
   `getBlock` 对未生成区块是用地形高度做**近似**的，那种「近似实心」一旦当真，走到边界就会被人顶上一层**隐形地面**；
3. 向上每次 1 格、最多 `PUSH_UP_LIMIT=8` 格（一棵树最高 6 格）；上不去就回退，再向四个水平方向各试 1~`PUSH_SIDE_LIMIT=3` 格；
4. 都走不通就**原地不动返回 null**，下一帧再审 —— 不许把人顶出世界，也不许每帧抖一次；
5. 成功时发 `teleport` 事件：这是刻意位移，D2 位置监视器靠它做豁免，否则 `回归.D2e` 会把救援记成可疑瞬移。

**实测**：

| 场景（e2e 第 33 节实测读数，源码与打包版各跑一遍，数字一致） | 结果 |
| --- | --- |
| 人为往身体里塞两格石头 | **18~19ms 内顶出**，`dy=2`（正好站上新方块顶面，一格不多），rescues 1→2 |
| 树苗长在玩家那一格（真实 `tickSaplings → growTreeAt`） | 树干 id=10 确实生成；**5ms 内顶出**，`dy=6`（从树干里钻出去） |
| 站在合法位置不动 1.5 秒 | 观察 91 帧：rescues **不变**、y 一格都不动（不许每帧顶人） |
| 未生成区块里的「近似实心」 | 直接调用 `pushOutOfSolid()` 返回 **null**，位置不动（y=15，地表≈17） |
| 同一处区块生成完之后再埋两格 | 区块 29ms 生成好，**15ms 救出**，`dy=2`（闸门不是永久拦死） |
| 帧率代价 | 16.1 真实 55fps、`world.update 9.3ms`（顶出检查每帧一次，看不出开销） |
| 与 D2 监视器的关系 | 累计跳变仍为 **0**：救援发 `teleport` 事件，按「刻意位移」豁免 |

**防假实现**（e2e 第 33 节 TC.1~TC.8）：
`TC.1` 埋两格后必须在几帧内被顶出且 `embedRescues` 计数增加（证明接进了主循环，不是只写了函数）；
`TC.2` 落点最小——正好站到新放那格的顶上（一格都不许多）；`TC.3/`TC.5` 位移有界（≤8 上顶 / ≤3 侧移）；
`TC.4` 走的是 `tickSaplings → growTreeAt` 的**真实生长路径**，并先断言树干 id 真的出现在玩家那一格；
`TC.6` 站得好好的时候 1.5 秒观察窗口内救援计数与 y 都不许变（防「每帧顶人」这种最坏实现）；
`TC.7` 未生成区块里直接调用 `pushOutOfSolid()` 必须返回 null 且位置不动；
`TC.8` 等那一块区块真正生成之后再手动塞两格石头，必须被救出来（证明 TC.7 的 null 是闸门而不是永久拦死）。

**单测**（顶出 P1~P5）：空位不许无端顶人、埋 3 格只顶到第一个能站下的位置（低一格就还卡着）、
整列塞满到世界高度时必须回退或走水平且不许送出世界、未生成区块的近似实心不触发、
生成完之后同一处必须能顶出（后两条成对，防止「闸门」其实是「函数坏了」）。

### 蜘蛛（2026-10-23 长期作业轮新增，6 条单测 + 9 条 e2e 断言，把「线只有羊毛一个来源」这条简化补全）

### 苦力怕（爆炸破坏方块，2026-10-23 长期作业轮新增，11 条单测 + 8 条 e2e 断言）

新增敌对生物 **苦力怕**：`hp 20`、走得不算慢（`speed 2.5`）、**不近战**，而是靠近玩家后开始
「嘶——」充能 `1.5 秒`（模型胀大并闪白，`sfx.hiss`），到点在自身位置起爆；
充能途中玩家跑出 `6 格` 就取消（原版那种「点燃了你还可以逃」的手感）；
起爆前被击杀则正常掉 `火药 1~2`，**自爆不留掉落**。夜里生成池 `NIGHT_TYPES` 加入 creeper。

**爆炸核心单独抽成纯逻辑** `core/explosion.js`（不碰 THREE/DOM，所以能在 Node 里直接测）：
- `explosionCells()`：以爆心为单位做球形遍历，**硬上限 power+1**（绝不出现「远处凭空少一格」），
  外圈 `(power, power+1]` 这层按线性概率参与抖动 —— 换一颗随机种子形状就变，同一种子结果完全一致（可复现）；
- `breakableAt()`：只挖「已真正生成的区块里的实心方块」，并拒绝**基岩、水、熔炉、箱子**
  —— 后两类的内容存在 `world.furnaces` / `world.containers` 里，把方块炸掉会留下无主状态（原版会连方块一起掉，本作先保守处理，记为差异）；
- `explosionDamage()`：贴脸满伤害 `12`，按 `(1-d/range)²` 单调衰减，`range=6` 之外归零；创造模式不受伤。

**结算走正常链路**：`game.onCreeperExplode()` 用 `world.setBlock(..., AIR)` 逐格移除，
因此脏标记、光照、网格、存档 diff 全都沿用既有路径（T2 的分帧预算负责排空），不会出现「数据没了、画面还留着」。

## 三、已知问题与限制

1. **纵向高度固定 64 格**：世界底部基岩、顶部 64，超过 56 格的高山会被截断（保证内存与网格化性能）。
2. **极端坐标精度**：距离原点约 ±3 万格以后，顶点浮点精度会导致抖动；正常游玩范围（数千格）无影响。
3. **阴影实现方式**：采用烘焙天光 + AO（树叶/方块会遮挡天空光形成暗部），未使用实时阴影贴图；
   因此「动态投影」不随太阳角度移动，这是体素游戏的常见做法（原版 MC 亦如此）。
4. **首次进入需点击画面**才能锁定鼠标并激活声音（浏览器/Chromium 的自动播放策略）。
5. **熔炉不单独保存「明火」标志**：读档时炉内燃料与产物照常恢复；若还有燃料与可烧炼物，下一帧会自然重新点燃，
   否则保持熄灭（12.13 用例会先烧完燃料再存档，因此能确定地验证「熄灭态不会被存档复活」）。
6. ~~生物之间没有互相碰撞，群聚时会重叠~~ **已实现**：挤在一起的同体会互相让位（按各自 AABB 宽度推开、
   被方块挡住的一侧把推力让给另一侧，绝不挤穿墙）。**生物与玩家之间仍然可以互相穿过**（原版如此，且实测
   推开生物不会把玩家挤动，见 e2e `SP.4`）。
7. ~~无自动上台阶~~ **已实现（T4）**：贴地行走会自动登上 1 格高台；潜行时不触发（想贴着边缘不下落仍可按住 Shift）。
8. **创造模式飞行**只能靠双击空格或 `F`，没有更细腻的升降手感。
9. **装饰植物会占据准星目标**：对着高草按右键时本作会自动把「命中的植物」归一化成它下方的地面来种植，
   但想在植物正上方叠方块仍需先清掉植物（与原版手感略有差异）。
10. ~~仙人掌不会造成伤害~~ **已实现（T4）**：碰到仙人掌表面或站在上面都会持续掉血（创造模式除外）；
   南瓜灯与荧石亮度相同（都是 15），仍属简化实现。
11. **箱子为单个 27 槽容器**：没有大箱子合并；被破坏时内容物全部掉在地上，不会随箱子物品一起转移。
12. **Windows 7/8 与 32 位系统未测试**（Electron 33 需要 Windows 10/11 64 位）。
13. 若显卡驱动异常导致黑屏，可用 `方块世界.exe --disable-gpu` 走软件渲染（已随包提供 SwiftShader）。
14. **床是单格方块**（原版占两格、分床头床尾）：本作整格都是床，贴图区分床头/床侧/床顶。
15. **睡觉的回血是本作规则**：恢复「损失生命的一半」，原版床只设重生点不回血；睡觉也不会清除附近敌怪。
    本作已有雨/雪且**睡觉会放晴**（与原版一致），但还没有雷暴与闪电可跳过。
16. **创造模式睡觉**只推时间与设重生点，不回血（创造本就不会掉血）。
17. **羊毛 ↔ 线 双向都有配方**（2026-10-23 T4 之后）：蜘蛛会掉线、4 线可合成 1 羊毛（与原版一致）；
    同时保留本作便利「1 羊毛 → 2 线」（原版没有，但既有验收断言与旧存档依赖它，删掉等于放宽基线）。
    两条共存不构成刷材料：4 羊毛 → 8 线 → 2 羊毛 是净亏损的往返。
18. **插在地上的箭 25 秒后消失**；骷髅射出的箭命中方块即消失，不插地留存、不可拾回。
19. **弓没有拉弓动画**：第一人称手持模型在蓄力时保持原样，只有 HUD 蓄力条与弓弦音效提示；也没有瞄准放大。
20. ~~**读档 / 批量改方块时会有长帧**~~ **已实现（2026-10-23）**：读档改成分片灌区块 + 片间让帧，批量改方块改成排队，
    实测整局累计最长帧从 2547ms 压到 200~300ms，其中读档期间 100~133ms、批量改方块期间 17ms。
    残留限制：**单个区块的生成/光照/网格是不可分割的**（常规 2.5 / 1.2 / 10.5ms，实测峰值 5.8 / 18.7 / 25.3ms），
    所以有待办的帧最差仍是 60~90ms；再往下要切网格化本身，本轮未做。读档墙钟 +80~90ms。
21. **羊毛再生按时间长回（90 秒）**：原版要羊主动吃草才长毛，本作没有「羊吃草」这个行为，
    所以剪完后站着不动也会长回来；剪毛动作也没有专属音效（借用一声轻「合成」音 + 羊叫）。
    剪刀同样不会加快破坏树叶/蜘蛛网（本作没有蜘蛛网，树叶仍按原速度破坏）。
22. **繁殖节奏是压缩过的**：原版繁殖冷却约 5 分钟、幼崽长大约 20 分钟、羊要吃草才长回毛；
    本作分别是 **60 秒 / 120 秒 / 90 秒**（让玩家在一次游玩里看得见循环）。
    另外没做近亲繁殖限制与繁殖次数上限，幼崽也没有独立叫声。
24. ~~**火药目前没有用途**~~ **已实现（P5 + 滚动任务 2）**：4 沙 + 5 火药合成 TNT，打火石点燃后 3 秒引信爆炸；
    另有深度 1 的有限连锁与被水淹没时的湿火药规则。烟花仍未实现，火药目前只有 TNT 这一条用途。
23. **蜘蛛是本作简化版**：没有专属音效（受击/死亡借用僵尸的叫声）、没有蛛网方块与「被网住减速」、
    不会跳扑玩家、也没有原版洞穴蜘蛛那种大小两种体型；只实现了「贴墙向上爬 + 近战咬人 + 掉线」这一条主干。
25. **村庄是探索切片，不是完整村庄系统**：只有一座确定性小村、一个农夫职业、三条固定交易（无动态价格/补货/声望），
    村民不会自动繁殖或重新生成；玩家造成的破坏与死亡会正常保留。村庄只在**新建世界**时生成，
    旧存档不会补建（避免把建筑硬塞进已经探索过的地形）。
26. **雷暴是简化版**：闪电不点燃方块/不劈出火（本作没有火焰蔓延），也不会把苦力怕变成充能状态；
    没有避雷针与落雷点方块破坏；闪电伤害按本作护甲规则走 `explosion` 类型（盾牌不挡）。
    雷暴只在雨天成立，雪天不会打雷；自然落雷只在玩家周围 6~15 格，不会劈到未加载的远方。
27. **地图是探索快照，不是实时小地图**：只在跨区块/打开面板时记录顶层方块，地下矿洞与高度差不会单独呈现；
    5×5 区块以外不显示；未加载但曾探索的区块仍保留旧快照（不会因方块变化自动重画）；旧档从空白开始。
    指南针只指向床/世界出生点，不指向最近村庄或宝藏。
28. ~~**实体不吃雾、也不吃体素那套亮度曲线**~~ **已实现（2026-11-06 P1 第 3 刀）**：
    生物现在按**自己眼睛所在那一格**的世界光采样材质色（`core/entitylight.js`，常数与 `VOX_FRAG` 同一组：
    平坦 `0.065+0.935·v^1.12` 与光池 `0.045+0.955·v^1.80` 按 `blkDom` 混合），
    并留了 `ENTITY_LIGHT_FLOOR = 0.16` 的可见度下限（全黑处仍看得出剪影，本作设计约定）；
    `scene.fog` 现在与体素雾用**同一份颜色与同一组 near/far**（体素 `ShaderMaterial` 显式 `fog:false`，
    因为雾是它自己在 `VOX_FRAG` 里做的）。验收：单测 `P1 实体亮度/P1 实体着色`、e2e `EL.1/EL.2`。
    **残留限制**：① 内置雾是线性插值、体素是 `t²`，44~88 格之间生物会比地形略浓一点（起止点与颜色一致）；
    ② `world.brightnessAt`（`0.05+0.95·v^1.15`）与 `lighting.lightToBrightness`（`0.06+0.94·v^1.25`）
    仍是另外两条曲线，被生成判定与既有断言读取，本轮没有统一它们；
    ③ T3 的另一半 —— 六只生物的 16×16 程序化脸贴图与部件比例 —— **本轮未做**（预算不足，做半套会更不一致）。
